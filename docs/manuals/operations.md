# Operations and maintenance

## Run as a service

The quick setup script starts the server in the foreground for development.
For ongoing use, run the built executable under an operating-system service
manager as a dedicated account. Use an absolute working directory and config
path. Ensure that account can read the TLS key and write the configured
database and log paths.

For public hosting, point DNS to the server host and put a trusted TLS proxy
such as Caddy in front of the application. Keep the application's backend
listener on loopback and expose only the public HTTPS proxy. Follow the
[domain deployment guide](../domain-setup/README.md) for DNS, certificates,
and proxy configuration.

On Linux with systemd, generate a user-service unit after building:

```sh
./scripts/setup.sh service-unit config/server.conf
```

The command writes `build/deployment/http-server.service` and prints install
commands. Review `ExecStart`, `WorkingDirectory`, and `ReadWritePaths` for the
database and log paths in your config before enabling the unit. It runs as the
current user's service; it does not install packages or change system-wide
services. To start a user service at boot without an interactive login, enable
user lingering with your system administrator.

## TLS and secrets

The development certificate generated by `setup.sh` is self-signed. Use a
certificate trusted by your clients for a shared deployment. Keep the private
key, generated runtime config, admin token, and user database restricted to
the service account and administrators.

Account, administration, and print requests require HTTPS. Review the
[TLS guide](../tls.md) and [security guide](../security.md) before exposing the
service to the Internet. The security guide explains request limits,
blocklisting, session handling, and the current limits of phone verification.

## Logs and health checks

Configure `log_level`, `log_console`, `log_file`, `log_directory`, and
`log_retention_days` in `server.conf`. Console output is useful for a
foreground session; file logs are useful for service-manager deployments.
Log files use a date in their filename. Avoid enabling debug logging in a
public deployment when request payload details could contain private data.
Log entries include millisecond timestamps and request IDs. At debug level,
request summaries omit query strings and include status, byte counts, and
duration; authorization, cookie, and API-key values are redacted. File logs are
buffered and warning/error messages are flushed immediately. A sudden process
termination can leave the most recent buffered info/debug entries unwritten.

Check these when investigating an issue:

1. Confirm the server process is running and the configured port is reachable.
2. Check the server log for configuration, TLS, database, or CUPS errors.
3. Run `./scripts/setup.sh cups status` and verify at least one queue is ready.
4. Run `./scripts/setup.sh --check` to rebuild and verify the setup.
5. Check that configured certificate/key and database paths are readable or
   writable by the service account as needed.

Use `GET /healthz` for process liveness and `GET /readyz` for SQLite
readiness. Readiness does not indicate that a printer is reachable.

The print page refreshes job status from CUPS when the user opens or refreshes
job history; job state is not pushed live to the browser.

## Database backups

Create a consistent SQLite snapshot while the server is running:

```sh
python3 scripts/backup_db.py
```

The default output is under `backups/`. The script uses SQLite's online backup
API, verifies the snapshot, and writes it with restrictive permissions. For a
custom database path, pass the database file and backup directory as
positional arguments:

```sh
python3 scripts/backup_db.py /path/to/server.sqlite /path/to/backups
```

Keep backups encrypted and access-controlled like the live database. Test
restores periodically: stop the server, preserve the current database, restore
a selected snapshot to the configured path, then start the server and verify
accounts and print history before returning to service.

## Tests and benchmarks

Run the build and automated test suite from the repository root:

```sh
cmake -S . -B build
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

The [benchmark guide](../benchmarking.md) describes the load generator,
limits, and metrics. Run load tests against a development instance rather than
a production printer server.
